# الأداء والموثوقية (Performance & Reliability)

> الحالة: معتمد للتنفيذ | القرارات: D-005, D-018, D-019, D-022 | يعتمد على: architecture.md §12-13, environments-and-devops.md §9-11, notifications-strategy.md §6, quality-and-testing-strategy.md
> **ملاحظة:** الأرقام أهداف أولية (SLO) تُعايَر بقياسات الإطلاق الفعلية، وتتحول إلى ميزانيات رسمية بقرار موثق. لا تُعدَّل لتناسب شيفرة متأخرة؛ الشيفرة هي التي تُعدَّل لتناسبها.

## 1. المبادئ
1. **الموثوقية ميزة منتج:** منصة سلامة عائلية: فشلها قد يعني خطرًا فعليًا.
2. **تدرّج الالتزام:** ما يخص السلامة (SOS، التنبيهات الحرجة) أعلى التزامًا من باقي المنصة.
3. **القياس من تجربة المستخدم (SLI)** لا من حالة الخوادم فقط.
4. **ميزانيات أداء تُفرَض آليًا** في CI وفي الإصدار.
5. **تدهور آمن:** عند العطل تبقى القدرات الأساسية، والحالة تُعلَن بصدق (D-018).
6. **الأسواق الحقيقية:** شبكات ضعيفة، أجهزة متواضعة، بطاريات محدودة.

## 2. أهداف مستوى الخدمة (SLO)
| الخدمة | المؤشر (SLI) | الهدف |
|---|---|---|
| واجهات التطبيق (قراءة) | نسبة طلبات ناجحة بزمن < 500ms | ≥ 99.9% شهريًا |
| واجهات (كتابة) | نجاح خلال < 1s | ≥ 99.9% |
| الدخول/OTP | نسبة نجاح تسليم OTP خلال 30s | ≥ 98% لكل دولة |
| **SOS** | تسليم للجهات (push) خلال 5s (p95)، وإنذار مُصعَّد ناجح | ≥ **99.95%** توفر المسار |
| الإشعارات C1/C2 | زمن الحدث→الجهاز p95 | C1 < 5s، C2 < 15s |
| المراسلة | تسليم رسالة بين متصلين p95 | < 1s |
| الموقع | زمن ظهور تحديث الموقع للمشاهد p95 | < 10s (نشط) |
| التزامن/المزامنة | اتساق خلال | < 30s بعد عودة الاتصال |
| حسم الإعدادات | زمن `effective` p95 | < 50ms (ذاكرة)، < 150ms (قاعدة) |
- **ميزانية الخطأ (Error Budget):** عند استهلاك 50% منها: تجميد الميزات غير الحرجة لصالح الاعتمادية في المسار المتأثر.

## 3. ميزانيات أداء التطبيق (جهاز مرجعي متوسط)
| البند | الميزانية |
|---|---|
| بدء بارد (حتى شاشة تفاعلية) | < 2.5s متوسط الأجهزة، < 4s الأجهزة المنخفضة |
| بدء دافئ | < 1s |
| الإطارات | ≥ 95% بلا jank (60fps) في الشاشات الرئيسية؛ 120Hz حيث يتوفر |
| الذاكرة | < 250MB ذروة عادية؛ لا تسرب في جلسة ساعتين |
| حجم الحزمة | < 60MB (أندرويد AAB تنزيل)، يُراقَب لكل إصدار |
| **البطارية** | استهلاك إضافي للموقع في الخلفية ≤ 3-4% يوميًا على الجهاز المرجعي (هدف مبدئي، يُعايَر) |
| البيانات | الاستخدام اليومي العادي < 20MB دون وسائط |
| الشبكة الضعيفة | الشاشات الرئيسية قابلة للاستخدام من الكاش/المزامنة على 3G و«lie-fi» |
| الشاشة الأولى | عرض فوري من القاعدة المحلية (Offline-first) ثم تحديث |
- أجهزة الأطفال المنخفضة الإمكانات (ذاكرة 2GB) **عنصر تصميم**، لا حالة استثنائية.

## 4. ميزانيات الخادم والبيانات
- API p95 (حسب الصنف): قراءة بسيطة < 100ms، قراءة مركبة < 300ms، كتابة < 200ms (دون زمن الشبكة).
- **استعلامات القاعدة:** لا استعلام يتجاوز 100ms p95 دون موافقة؛ كل استعلام جديد يمر بـ `EXPLAIN` في CI على مجموعة بيانات صناعية كبيرة.
- **RLS:** كلفتها مقاسة، وفهارس تبدأ بـ `family_id`.
- **لا N+1:** اختبار آلي لعدد الاستعلامات لكل نقطة نهاية.
- **Redis:** زمن < 5ms، ونسبة إصابة الكاش للحسم ≥ 95%.
- **WebSocket:** إعادة اتصال بتراجع مع تشويش (jitter) لمنع «العاصفة المتدافعة» (thundering herd).

## 5. نموذج السعة (Capacity Model)
### 5.1 الافتراضات (تُحدَّث بالبيانات)
```
عائلات F، أفراد/عائلة M (≈4-5)، أطفال بأجهزة C (≈1.5)
نشاط ذروة: 20-30% من الأجهزة متصلة WebSocket
الموقع: نقطة كل t ثانية للأجهزة النشطة (t متكيّف 30-300s)
رسائل: m/فرد/يوم
```
### 5.2 مراحل التحجيم
| المرحلة | العائلات | الغرض |
|---|---|---|
| S-A | حتى 50 ألف | الإطلاق، خلية واحدة |
| S-B | حتى 1 مليون | خلية أو خليتان، قراءة منسوخة، فصل المهام |
| S-C | 10 مليون+ | خلايا إقليمية، تقسيم الموقع والرسائل، استخراج `realtime` و`location` |
- **اختبار حمل لكل مرحلة** قبل بلوغها بهامش 2×، ومقاييس إنذار مبكر (استخدام اتصالات قاعدة البيانات، طول الطوابير، حجم الجداول المقسّمة).
- **أثقل الأحمال:** نقاط الموقع (كتابات مستمرة) واتصالات WebSocket؛ تُعزل مبكرًا (طابور مخصص، كتابة دفعات، جداول مقسمة زمنيًا بسياسة احتفاظ).

## 6. التدهور الآمن (Degradation Matrix)
| العطل | السلوك | ما يُعلن للمستخدم (D-018) |
|---|---|---|
| Redis | الحسم من القاعدة، تعطل مؤقت للحدود/الحضور | لا شيء أو بطء مؤقت |
| مزوّد SMS/OTP | تبديل لمزوّد/قناة بديلة | تأخير محتمل لرمز الدخول |
| مزوّد Push | قناة بديلة للحرج (SMS/اتصال)، والداخلية تبقى | لا |
| WebSocket | الاستقصاء + الدفع، تعمل المزامنة عند الفتح | «يتأخر التحديث الفوري» |
| مزوّد الذكاء | تبديل نموذج/مزوّد ثم تدهور لميزات غير ذكية | «المساعد غير متاح الآن» |
| الخرائط | عرض الإحداثيات/قائمة الأماكن | شرح مختصر |
| القاعدة الأساسية (قراءة فقط) | وضع قراءة، وSOS عبر مسار مستقل | بانر صادق |
| منطقة كاملة | تحويل (§8) | حالة خدمة |
- **مسار SOS مستقل (Isolated Path):** لا يعتمد على تحديث ثقيل أو مزوّد وحيد أو خدمات غير ضرورية، وله مجموعة مزوّدين وقنوات احتياط وخدمة مراقبة خاصة.

## 7. دعم الاتصال الضعيف والـ Offline
- **كتابات معلّقة (Outbox محلي):** رسائل، تحديثات، موافقات (مع وسم الوقت)، وتُسوّى بإصدار الصف.
- **المزامنة التزايدية** بمؤشر (cursor/seq)، لا تحميل كامل.
- **ضغط الحمولات** وتقليل الحجم، وتأخير الوسائط الثقيلة على شبكة محدودة (يحترم «توفير البيانات»).
- **إعادة المحاولة الذكية** بتراجع وتجميع، وإيقافها عند البطارية الحرجة للميزات غير الحرجة.
- **الموقع:** تكيّف معدل أخذ العينات (حركة/سكون، بطارية، خطر)، وتجميع قبل الإرسال.

## 8. الاستمرارية والتعافي من الكوارث
- **أهداف:** RPO ≤ 5 دقائق، RTO ≤ 1 ساعة للمنصة؛ مسار SOS: RTO ≤ 10 دقائق.
- **نسخ احتياطي:** PITR، ونسخ عبر مناطق ضمن قيود الإقامة (D-022)، ومفاتيح التشفير بنسخ آمنة مستقلة.
- **ثنائية المنطقة (Active-Passive)** لكل خلية إقليمية حيث تسمح الإقامة، وخطة تحويل مجرَّبة.
- **تمارين التعافي (Game Days)** ربع سنوية: فقد قاعدة، فقد منطقة، فقد مزوّد push، فقد مفتاح (مع اختبار استرجاع).
- **اختبار فوضى** مستمر في staging.

## 9. إدارة التغيير بأمان
- نشر تدريجي (Canary) مع مقاييس حماية وإيقاف تلقائي (environments-and-devops §5.4).
- أعلام الميزات لكل خدمة؛ **ممنوع تغيير يمس SOS/Notifications الحرجة في أوقات الذروة/الأعياد** دون موافقة (نوافذ تجميد).
- ترحيلات expand/contract، ولا ترحيل ثقيل بلا اختبار على حجم مماثل.

## 10. الرصد والتنبيه
- لوحة SLI/SLO لكل مجال، ومعدل استهلاك ميزانية الخطأ، وتنبيهات احتراق (burn rate) سريعة/بطيئة.
- **اختبارات اصطناعية (Synthetic)** مستمرة: دخول، رسالة، إشعار، SOS تجريبي (حساب مختبر)، من مناطق متعددة.
- **تقارير RUM** من التطبيق: بدء، إطارات، أخطاء شبكة، حسب الجهاز والدولة والشبكة.
- **تنبيهات:** SOS ≥ دقيقة، C1 تأخر، فشل OTP لدولة/مزوّد، ارتفاع أخطاء الدفع، امتلاء قاعدة، طول طابور حرج.

## 11. الكفاءة والتكلفة
- أداء لكل دولار: كلفة الرسالة/النقطة/الإشعار، وميزانية الذكاء (ai-strategy §12).
- مراجعة ربع سنوية لأعلى 10 كلف.
- تحسين السعة ببيانات (Right-sizing)، وإيقاف غير الإنتاج خارج الدوام.

## 12. معايير القبول
1. PR-AC-01: لوحة SLO لكل المجالات تعمل قبل الإطلاق التجريبي، ومعرّفة الأهداف بالأرقام أعلاه.
2. PR-AC-02: اختبار حمل يثبت تحمل S-A بهامش 2× دون تجاوز SLO.
3. PR-AC-03: زمن حسم الإعدادات p95 < 50ms/150ms وفق الاختبار.
4. PR-AC-04: لا نقطة نهاية بنمط N+1؛ استعلامات جديدة تحمل خطة EXPLAIN مقبولة في CI.
5. PR-AC-05: ميزانيات التطبيق (بدء، إطارات، ذاكرة، حجم، بطارية) تُقاس في CI/ليليًا على أجهزة مرجعية وتفشل الإصدار عند التجاوز.
6. PR-AC-06: تعطّل Redis أو مزوّد Push أو SMS لا يمنع الدخول ولا SOS (اختبار فوضى).
7. PR-AC-07: عند فقد الاتصال تعمل القراءة وتُجمَّع الكتابات وتُسوّى بلا فقد (اختبار عمليات مقاطعة).
8. PR-AC-08: تمرين تعافٍ ناجح موثق قبل الإطلاق العام، وتحقيق RPO/RTO في المحاكاة.
9. PR-AC-09: SOS الاصطناعي المستمر يعمل ويُنبّه عند الفشل خلال دقيقة.
10. PR-AC-10: لا ميزة جديدة تُدمج دون ميزانية أداء مقاسة للمسار الجديد.
